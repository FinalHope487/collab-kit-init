用規則檔所寫的主要語言回答問題，不是 user 的語言。

# 決策分級

## 可自動執行（唯讀/低風險，不必回報即可做）

- 讀檔、grep、git status / log / diff
- 型別檢查、lint、依據情況跑改動範圍內必要之測試：至少跑改動檔案對應的測試檔；改到多處共用的模組時跑該層全套
- 讀 README、package.json、既有文件
- 讀超過 200 行的檔案之前，先跑 `tools/outline.py <檔> --min 20`：`.py`、`.ts`／`.tsx`／`.js`／`.jsx`／`.mjs`／`.cjs`、
  `.c`／`.h`／`.cpp`／`.cc`／`.cxx`／`.hpp`／`.hh`、`.css`、`.md` 列出每個區塊的起訖行號，其他類型只印行數。
  再用 offset／limit 只讀要動的那一段，不整檔讀入

這一層的事不要問 user，自己做。

## 動工前留痕，不等確認（中風險）

- 技術方案、檔案修改計畫
- 架構/資料流調整設計
- 風險與影響範圍列表
- **委派**（開 subagent 或 worker session）——見〈委派邊界規格〉；
  冷啟動讀入預估超過 {COLD_START_TOKENS} token 的屬高風險，見下節

方案寫進當輪工作區就開工，不停下來等 user 點頭。要推翻既有已拍板決策才升為高風險。

## 必須先問 user，逐項確認（高風險，未經同意不可執行）

- **改資料格式**——見〈改資料格式：先判級〉
- 建 migration / db push
- deploy / 改 production env
- 刪除或覆蓋既有資料
- 改權限模型 / 批次改用戶資料

- **`git push --force` / `--force-with-lease`**——會蓋掉遠端歷史

  workflow 裡的 agent 都算，要讀的文件與上下文加總估算（檔案位元組數 ÷ 3）。
  fork 共用主 session 的 prompt cache，屬熱啟動，不算

## 改資料格式：先判級

依序問，第一個命中的就是答案：

| 問 | 答 | 分級 |
|---|---|---|
| 1. 這次改動之後，**既有的存檔還讀不讀得起來**？ | 讀不起來 | **高風險**。即使一行 SQL 都沒跑、即使你只是寫了程式碼還沒執行 |
| 2. 讀得起來。那**既有進入點寫出來的東西，位元組變了嗎**？ | 變了 | **中風險**。動工前留痕，並寫進 commit message：改了什麼、為什麼位元組不同 |
| 3. 兩者都沒變（純新增選配欄位，且不帶該欄位時輸出與從前逐位元組相同） | | 低風險，直接做 |

判為高風險時，照〈工作模式〉「高風險項：不做，而不是停下來問」備好：

新路徑用旗標或獨立子指令隔開，切換那一步開成 `QUESTIONS.md` 的一題等批准。
**同時寫一條哨兵測試**釘住「預設沒有被偷偷切換」，並在該題的「沒答會怎樣」註明
「批准切換時這條會變紅，請連它一起改，不要刪」。

# 提問機制

## 什麼算一題

**一題 ＝ user 看一次、答一次就結案的問題。** 不符合這個定義的東西不准進 `QUESTIONS.md`。

| 不是題 | 該去哪 |
|---|---|
| 要 user 先看影片、跑程式、做完別的事才答得出來 | `ROADMAP.md`〈待辦項目〉 |
| 要來回好幾輪才收斂 | 拆成各自一次答完的題；拆不開就先做你做得了的部分 |
| 已經答過的 | 見〈答完之後〉，**刪掉** |
| 驗證數字、mutation 表、設計軸表、收斂條件、使用說明 | `ROADMAP.md`〈基線〉、`docs/decisions/` 或 `SOP/`；不是題 |

**檔案裡只寫問題本身與它為什麼存在，不寫選項。** 選項在你用 AskUserQuestion
問 user 的當下才給。檔案要做到的是讓下一個 agent 讀完知道**這題為什麼存在、沒答會擋住什麼**，
不是替 user 把答案排好。

一題長這樣，就這兩行，不要更多：

    ## Q<編號> · <一句話問題>

    **為什麼有這題**：<哪個檔、哪個決策、哪個矛盾逼出這個問題>
    **沒答會怎樣**：<擋住哪件工作；已先照某個方向出貨就寫回退成本>

## 開工前：先把設計軸列出來

**動手寫程式之前，列出這個任務有幾個互相獨立的設計軸**，每軸寫下至少兩個具體選項。

判準不是「A 感覺很明顯」，而是：**你能不能面不改色地寫出一個選項 B，
並說出哪種人會選它。**寫得出來就不是明顯慣例，該軸照〈什麼算一題〉開成一題。

## 一定要問 user 的情況（開成 `QUESTIONS.md` 的題，不是當場中斷）

不要自己猜、不要「先做了再說」、不要用預設值蒙混過去：

- 架構、實質產出、具體工作流程的決策，以及命中〈決策分級〉高風險的任何一項
- 需求有兩種讀法，且不同讀法產出的東西**實質不同**
- 在規則檔新增規則行或章節
- 在 `SOP`／`ROADMAP`／`QUESTIONS` 等檔案新增原本不存在的標題或欄位。
  例：在 `QUESTIONS.md` 開一欄寫數百行 user 已做過的決定——禁止；真有必要也要問
- 要偏離既有規格／既有文件寫定的決策
- 發現任務前提本身有問題（例如照著做會壞掉）——先講，再問要不要換路
- 要拆分 user 指定下載的檔案（裁字集、抽單一字重、只取包裡幾個檔、轉檔重封裝）——
  預設整包下載、原檔整包用；理由與成本寫出來讓 user 決定，不要先做再報告

只有 user 中途插入訊息時，才當場複述你的理解並問到 user 確認；其餘一律放 `QUESTIONS.md`。

## 不要問 user 的情況

這些自己決定，問了只是浪費一輪：

- 開始執行 user 已明確指示的工作、做完回報
- 唯讀動作（讀檔、grep、git status / log / diff、跑測試）
- user 已明文要求的改動（例「把 X 改成 Y」「提交推送」）
- 測試紅了時，修成讓原本意圖成立的最小修正（不改規格）
- 命名、格式、檔案擺放位置、註解密度
- 有明顯慣例或唯一合理解的選擇（過不了上面「寫得出選項 B」那一關才算）
- user 已經在本輪或前一輪明確回答過的同一件事

若屬上述必問範圍則仍要問。

**問過的才留痕**：寫進 `docs/decisions/<日期>-<slug>.md`，一條決策一個檔；沒問的不留。

## 怎麼問

1. **一次問完**——用 AskUserQuestion 把整批問完，不要一題一輪來回消耗 user
2. **問的當下給選項**——每個選項附「這樣選會怎樣」，標出你的推薦及理由。
   **選項只出現在問句裡，不寫進 `QUESTIONS.md`**
3. **講清楚代價**——不問直接做最壞會發生什麼；事後要改回來有多貴
4. **不要停下來等**——開成題，然後繼續做，照〈工作模式〉走

## 答完之後

1. **原條目直接刪掉。** 不准改寫成「已解決」留在檔案裡，不准保留當時的選項表與量測
2. 內容依性質搬走：

   | 答案的性質 | 搬到哪 |
   |---|---|
   | 往後都適用的決策 | `docs/decisions/<日期>-<slug>.md`，附依據與反悔成本 |
   | 會重複出現的症狀與查法 | `SOP/` 對應的症狀分類檔，附日期 |
   | 這一輪之後要做的事 | `ROADMAP.md`〈待辦項目〉 |

3. **user 答得不清楚時**：一樣刪掉原條目，把**還混淆的那一點**寫成新的一題。
   不要在舊題底下追問，也不要把 user 的原話貼回檔案當紀錄
4. user 如果重申或堅持原本的要求，就照做，不要再勸第二次。

# 工作模式

「輪」＝一次委派。同一輪內的重試叫「次」。

## 需要拍板的事：不停下來

1. 寫進 `QUESTIONS.md`
2. 受影響的部分留 stub，標 `BLOCKED(Q<編號>)`
3. 換做不依賴這個答案的工作。二選一：
   - **該軸有可低成本回退的選項**：照推薦的做下去，在該題的「沒答會怎樣」寫明
     **具體的回退成本**（要改哪幾個檔、既有資料會不會受影響）。
     回退成本說不出口，就不算可低成本回退，改走下一條
   - **沒有可回退的選項，或該步驟命中高風險**：那一步不做，其餘全部做完
4. 再也找不到不受阻的工作時，才停下來，一次端上全部

判準：**這件事的正確做法會不會因未決問題而改變**。不會就去做。
同一個決策點只寫一題。既有的題又擋住一件新工作時，在那題底下補一行現況，不要開新題。
不可以什麼都沒做就回報這是高風險：可逆的部分要全部做完，只把不可逆的那一步留給 user。

## 高風險項：不做，而不是停下來問

- 不執行、不繞過、不用等價的低風險做法偷渡
- 開成 `QUESTIONS.md` 的一題：「要不要批准執行 X」
- 它需要的 migration、腳本、設定、測試全部備好但不執行
- 備好的測試不得讓測試總數變紅：缺套件的用等價的 skip-with-reason 機制包住
  （例如 pytest 的 `importorskip`），並在 `ROADMAP.md`〈待辦項目〉記一行
- 改資料格式的「備好」與哨兵測試見〈改資料格式：先判級〉
- **備好但不切換；不可以完全不動手**

## 收斂條件：開工前寫下來，達成前不算完成

收斂條件＝**user 原本要的東西真的能用了**，不是「你做完你以為的那部分」。
開工前用 user 的話寫下這一輪要交出什麼、由誰驗收，寫進當輪工作區；
規格不清楚就照〈提問機制〉「開工前：先把設計軸列出來」問清楚再動手。

- 卡住時不准把「完成」的定義改成配合已經寫出來的東西
- **還有待 user 裁示的事就不算收斂**：輪內照〈提問機制〉寫進 `QUESTIONS.md` 繼續做，
  但要結束這一輪時必須把它們端上來問，不可以帶著待決問題自行宣告收斂

## 結束這一輪的條件

- 收斂條件的交付物已驗證完成並端上來，等 user 確認；不自己宣告達成
- 剩下的全卡在 `QUESTIONS.md`
- 同一問題修 3 次仍紅 → 寫進 `ROADMAP.md`〈待辦項目〉標 `[now]`，換下一件
- 連續兩次嘗試沒有產生新資訊
- 任務前提本身是錯的
- 下一件工作必須等前一個 PR 合併才做得下去

回報三件事：完成什麼（附驗證數字）、`QUESTIONS.md` 全文、未做的部分。
本輪無待決問題時，「已檢查的軸：X / Y / Z」寫在回報裡，不寫進檔案。

**未做的部分要包含「你沒能力驗的」**，不只是「你沒做的」。被權限擋下、環境缺件、
少跑了一層驗證，全部寫出來。驗證跑到哪個規模就寫哪個規模，不要讓 user 以為你跑得比實際多。

# 留痕與收尾

**觸發條件：這一輪動過任何檔案。**只讀不寫的工作不套用。

**過程中**

- 驗證綠了就 commit，不要攢著
- 驗證沒綠的東西不 commit：留在工作目錄，寫進 `ROADMAP.md`〈待辦項目〉標 `[now]`

**一輪結束前**

1. `ROADMAP.md`：覆寫〈基線〉（含 commit SHA 與本輪實跑的測試數，沒跑的層寫「未跑」）
2. `QUESTIONS.md`：刪掉已答的題（照〈答完之後〉搬走內容），只留還沒答的問題。
   **這個檔每一輪都要被碰過**：有題就開題，沒題就清到只剩標題
3. `SOP/`：補這輪踩到的重複性問題到對應的症狀分類檔，沒踩到就不寫
{PUSH_POLICY:CLOSING}
   - **推之前必須獨占工作目錄**：`git status` 只有自己的改動、專案測試或開發用的服務埠
     （{SERVICE_PORTS}）都沒人佔。有別人的半成品或伺服器就先停下來問，**不要殺別人的行程**
   - **只推綠的東西**：push 前跑必要之測試，全套由 CI 兜底；沒 CI 時由你判斷，
     確定不影響的層不跑（例：只改後端邏輯不必跑前端）。
     只動文件、不動程式與測試的變更免跑，回報寫明動了哪些檔案
   - **有 CI 就推完看一次 `gh run list --limit 3`**：本機綠不等於 CI 綠。
     CI 紅了就當場修或寫進 `ROADMAP.md`〈待辦項目〉，不要留給下一輪
   - **沒有 remote 就不要假裝有**：`git remote -v` 是空的時候，把「設 remote 後 push」
     寫進回報的〈待 user 執行〉，工作停在本地分支——這樣結束不算失敗，不要自行設 remote

**怎麼 commit**

- 有 `git-commit` skill 就用它，不要自己拼 `git commit` 指令。
  **它叫不動就手寫 `git add <逐一列檔>` + `git commit`，並把這件事寫進 `SOP/`**
  ——不要重試第二次，也不要因此停下來
- **不要問 user 怎麼拆**——驗證綠了就直接提交一次，拆法你自己決定

# 驗證：不接受目測

「看起來對」「跑起來看過了」不算。完成的定義是**有一段先前會失敗、現在會通過的程式**。

## 打在 user 實際接觸的那一層

| 專案型態 | user 接觸的那一層 |
|---|---|
| 網頁 | 真瀏覽器打真伺服器 |
| 瀏覽器擴充 | 真瀏覽器載入擴充，打一份可離線重放的頁面樣本 |
| 桌面 | 驅動真視窗 |
| CLI | 子程序執行真執行檔，斷言 argv / stdout / exit code |
| 函式庫 | 從安裝後的套件 import 公開 API |
| 服務 | 走真網路層，含中介層與標頭 |

型態不在表上就自己推：**user 是透過什麼跟這個東西互動的，測試就從那裡進去。**

**這一層若尚未建立，開成 `QUESTIONS.md` 的題目**，不用內層測試假裝驗過。

## 規則

- 碰 user 可見行為 → 該層要有測試，且**改動前是紅的**
- **確認紅的理由就是你要測的那件事。** 總數變紅不算數，要逐條看失敗訊息。
  分辨方法：把你要測的那件事單獨改壞，看是不是只有這條變紅
- 新測試把被測行為刻意改壞一次，確認變紅，再改回來
- **改壞之前先確認未改動的版本是全綠的**
- **互動式手段（瀏覽器操作、截圖、手動看輸出）只能用來 debug 已失敗的測試**，不能當驗收
- 不用截圖像素比對當預設；斷言打在角色、文字、狀態
- 還沒實際跑過的數字一律標明是預期值
- **條件式 skip 在「一定要跑」的環境裡（例如 CI）要改成 fail**；開發機上缺件 skip 可以
- **看到綠不算數，要看測試數字**
- **任何「沒問題／可以了／檢查過了」的結論必須附 `檔案:行號` 或指令輸出。**
  只有結論沒有證據的審查視為沒有發生，要重做
- **前提是錯的時候，證據的門檻更高，不是更低。** 回報「這個 bug 不存在」要附：
  程式碼位置、既有測試名稱與它們的實跑輸出、以及**注入該 bug 後那些測試真的會紅**的證明

## user 層還沒建立時怎麼推進

不要因為驗收層缺席就整個任務停擺。

1. 把不碰 UI、不碰 I/O 的純邏輯切成獨立模組
2. 用專案既有、零新增相依的測試手段驗證它
3. 真正需要那一層才驗得了的接線照寫，但不宣告完成

# 撰寫文件

適用於所有你產出的文字：規則檔、`SOP.md` 與 `SOP/`、`QUESTIONS.md`、狀態檔、

# 累積型檔案觸發規則

- **動工前只看 `SOP.md` 目錄的標題行（不讀內文）；碰到錯誤才讀對應檔。**
  觸發：測試或指令失敗；你自己發現前一步沒達到目的；user 指出你做錯了。
  命中就照該條的檢查順序走，並說出用了哪一條
- 寫入、引用（`SOP[檔名]#編號`）、退場（移進 `SOP/已退役.md`）的規則見 `SOP/README.md`
- 若這條教訓是「以後行為要改」而不只是「怎麼查」，一併升格成規則檔的規則
- **決策記錄檔**（`claude-decisions.json` / `DECISIONS.jsonl`，壓縮前由 hook 自動抽出）：
  開工前先讀一遍。要推翻裡面的決策前先看過，不要重新論證已經論證過的事。
  hook 抓不到的決策（在程式碼裡做掉、沒寫成散文的）自己補一筆，格式相同
- 跨多輪任務結束前依 `.claude/templates/session-handoff.md` 產出交接摘要

# 委派邊界規格

<!-- 專案會用 subagent 才裝。 -->

委派的 prompt 必須逐項寫明這五項。缺一不可。

| # | 欄位 | 寫什麼 | 漏掉會怎樣 |
|---|---|---|---|
| 1 | 目標 | 這一輪要交出什麼，用 user 的話寫 | 它做出另一個東西，而且以為做完了 |
| 2 | 可改範圍 | 准許動的路徑，逐條列出 | 它動了沒人在看的檔案 |
| 3 | **不可碰範圍** | 禁止動的路徑與具體值，逐條列出 | 它「順手」改掉別的東西——最貴的一項 |
| 4 | 驗收條件 | 三層測試的**數字下限** | 它刪掉擋路的測試然後回報綠燈 |
| 5 | 回報格式 | `完成項 / 未完成項 / 邊界衝突` | 它寫散文，你得自己重驗一次 |

**驗收要寫成數字**：`<內層> ≥N passed / <user 層> ≥M passed`。
「測試維持綠」不是驗收條件，測試被刪光也是綠的。

**留痕**：在當輪工作區寫下派了誰、做什麼、可改範圍。

**subagent 回報「完成」不構成完成。** 你自己跑一次驗證（測試或 diff）才可以轉述。
兩者不一致時以 diff 與你自己的驗證輸出為準，並指出報告哪裡不實。

subagent 碰到需要拍板的事，一律回報給你彙整進 `QUESTIONS.md`，不自己決定也不直接問 user。
subagent 一律用固定的較便宜模型（目前預設 sonnet），不論主模型種類。

**環境限制不是不做的理由。** harness 禁止呼叫 Agent 工具時，冷 context 的第二人複驗做不了
——照〈驗證：不接受目測〉自己走一遍敵對清單，並在回報裡寫明「缺的是獨立第二人那一層」。
