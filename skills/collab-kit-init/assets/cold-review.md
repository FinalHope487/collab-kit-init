# 冷審查

## 流程

push 之前，用乾淨的上下文審這個任務的全部程式碼改動。審查的合約是 `docs/spec.md`、`docs/plans/` 裡這個任務的計畫，以及 `DECISIONS.md` 新增的行。只動文件或測試的批次不審。

審查者，依序選第一個可用的：

1. 全新的獨立子代理：只給合約與 diff，不給主 session 的對話內容；prompt 明寫「只讀不改」。平台有內建審查指令時也可以用
2. 另一個 agent 工具：只有 `docs/project-rules.md` 明列該工具與授權範圍才可用。它永遠是選項，不是必要條件
3. 主 session 逐條自查合約與 diff。回報寫明「未經獨立審查」與原因

改動涉及公開契約、資料格式、模組邊界、資料流或已記錄的設計決策時，在 prompt 明寫「找出會破壞契約的反例」，用對抗式審查。

每一條審查意見都對照程式碼確認。意見不成立時，附檔案與行號當證據。確認是缺陷的，先寫出能重現它的測試再修。修完的 diff 換一個全新的審查者再審（備援第 3 層自查時不適用），直到審查者找不到會直接阻擋後續開發的問題。

## 名詞定義

- 阻擋後續開發的意見：對支援的輸入破壞了已核准的契約、讓公開入口彼此不一致、遺失或覆寫資料，或必須改公開介面才能完成已核准的後續工作。要指出是哪個契約或輸入，以及受影響的是哪項工作。
- 建議項：不符合上述阻擋條件的意見。記進 `ROADMAP.md` 的待辦。

## 額度

付費額度只在 user 實際授權的範圍內使用。專案在 `docs/project-rules.md` 記下核准的工具、操作與上限。審查者不可用、未登入、額度用完或低於專案設定的最低剩餘額度時，改用下一個選項，並在回報寫明改用了哪個與原因。遇到錯誤或逾時：先查額度，額度允許就重試一次。
